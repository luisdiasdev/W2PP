## 1. Executive Summary

`_MSG_MessageChat.cpp` implements `Exec_MSG_MessageChat`, the single entry point that consumes client opcode `_MSG_MessageChat` (raw `51`, wire value `51 | 0x100 | 0x200 = 819 = 0x0333`, `Code/Basedef.h:1439`). It is the only handler that writes the five per-session chat-mode flags (`Whisper`, `PartyChat`, `KingChat`, `Guildchat`, `Chatting`) and the only handler that implements the `guildon` / `guildoff` / `guildtax` / `guild` text commands. After interpreting those commands it relays the (truncated, optionally censored) message as a local "say" to every player inside the 33x33 view grid around the sender, and finally writes an audit line to the chat log file.

**Role in the system.** The component is a *social/administrative command multiplexer fused with a spatial broadcast relay*. It is the single consumer of the `MSG_MessageChat` client packet and, equally, the *producer* of `MSG_MessageChat` traffic generated by `SendSay` (`Code/TMSrv/SendFunc.cpp:1647-1660`) — the same wire structure is used both for player chat and for merchant/NPC "say" bubbles, so the handler's assumptions about the payload are shared with a non-player producer.

**Key findings (highest impact first).**

1. **A remote format-string vulnerability is reachable from this component through its audit path.** The client-controlled message text is formatted with `sprintf(temp, "chat, %s : %s", ...)` (`_MSG_MessageChat.cpp:201`), passed to `ChatLog` (`Code/TMSrv/Server.cpp:9225`), re-formatted into `LogTemp` and then written with `fprintf(fChatLogFile, LogTemp)` — a *non-literal format string* (`Code/TMSrv/Server.cpp:9244`; the same defect exists in `Log` at `Code/TMSrv/Server.cpp:6723`). Chat text containing `%n`/`%s` is therefore interpreted as a conversion specification by the server process. `_CRT_SECURE_NO_WARNINGS` is enabled project-wide (`Code/TMSrv/TMSrv.vcxproj:61,79`), so the compiler never flags any of the printf-family misuse in this file.
2. **The event-area chat censor is ineffective for messages longer than six characters.** `strncpy(m->String, "??????", 6)` (`:174`) copies exactly six bytes and *does not* append a NUL, so bytes 6..n of the original message survive verbatim; only the first six characters are masked. A message of 20 characters leaves 14 characters readable to everyone in view.
3. **The relayed packet's `Size` field is client-controlled and never normalized.** The handler rewrites `String`, `ID` and (twice) the string terminator, but never `m->Size`, and re-broadcasts the *same buffer* with `GridMulticast(..., (MSG_STANDARD*)pMsg, conn)` (`:193`). `CPSock::ReadMessage` only enforces `sizeof(HEADER) <= Size <= 8192` (`Code/CPSock.cpp:397`), and the per-opcode equality check `BASE_CheckPacket` is dead code (`return FALSE;`, `Code/Basedef.cpp:6585`). A client can therefore declare `Size = 8192` and have ~8 KB of its own receive buffer re-transmitted to up to 1,088 recipients per chat line, or declare `Size < 108` while the handler still writes at offset 12+95.
4. **`MessageChat` filters nothing and rate-limits nothing.** There is no flood control anywhere in the server for this opcode (no timestamp field, no counter; `CUser::LastChat` is the whisper last-correspondent name cache, not a throttle — `Code/TMSrv/CUser.h:78`, `Code/TMSrv/_MSG_MessageWhisper.cpp:1295-1368`). Every channel-opt-out flag this handler maintains (`whisper`, `partychat`, `kingdomchat`, `guildchat`, `chatting`) is **ignored by the local-chat path**, because `GridMulticast` never consults `CUser` flags: local chat is the one channel a player cannot opt out of.
5. **The `chatting` toggle is an orphan flag.** `pUser[conn].Chatting` is written here (`:161`), reset on account login (`Code/TMSrv/ProcessDBMessage.cpp:392`) and read by *no* code in the repository — the other four flags all have consumers (`_MSG_MessageWhisper.cpp:1169,1216,1320`, `SendFunc.cpp:278,1016`).
6. **Two correctness defects in `guildtax`:** `atoi(szString)` is evaluated on an **uninitialized stack buffer** when the player sends the bare command with no argument (because `sscanf` matched only one field, `:32-35`), and the once-per-day latch is reset at the end of each Colosseum cycle (`Code/TMSrv/Server.cpp:6404-6407`), not daily, contradicting the `_NN_Only_Once_Per_Day` message it emits.
7. **Dead code and an unused party-leader indirection:** `int leader = pMob[conn].Leader; if (!leader) leader = conn;` (`:189-191`) is computed and never used, and the `else` branch at `:195-199` ("wrong status") is unreachable because `Mode` is already gated at `:29`.

**Business surface.** 8 text sub-commands (`guildon`, `guildoff`, `guildtax`, `guild`, `whisper`, `partychat`, `kingdomchat`, `guildchat`, `chatting` — 9 tokens, 5 of them flag toggles), 1 spatial broadcast, 1 mailbox notification per command, 1 file rewrite (`Guild.txt`), 2 audit sinks (`TM_*.log`, `chat_log/TM_*.txt`).

**Quality assessment.** Afferent coupling 1, efferent coupling 14–16 (matches the architecture report's 14). The component is a single 184-line function with **zero** helper functions, one shared 4,096-byte global scratch buffer, no error reporting to the client for unknown commands, and no tests anywhere in the repository.

### 2.4 Data lifetime and sharing hazards

* The inbound buffer is **mutated in place** and then relayed (`:178-193`). This "zero-copy relay" means every normalization the handler omits (notably `Size`) is inherited by all 1,088 outbound copies.
* `temp` (`char temp[4096]`, `Code/TMSrv/Server.cpp:277`) is a single process-wide scratch buffer shared by the handler, `Log`, `ChatLog` and `SendNotice`; the handler uses it twice (`:91`, `:96`, `:201`) and its lifetime is never scoped to the function.
* `g_pMessageStringTable[MAX_STRING][128]` (`Code/Basedef.cpp:742`) is loaded at startup from `Language.txt` (`Server.cpp:7160` → `Basedef.cpp:4637`). That file is **not present in the repository**, so the exact rendered text of `g_pMessageStringTable[169]` and `_NN_No_Speak` cannot be verified statically. Note `memset(g_pMessageStringTable, MAX_STRING, 128)` (`Basedef.cpp:4639`, repeated at `:4934`) initializes only the first 128 bytes with the value `0xD0`, not the whole table — evidence that the table's initialization contract is itself unreliable.
* `TaxChanged[MAX_GUILDZONE]` (`Server.cpp:436`) is the *only* per-zone rate limiter in the tax command and is not persisted; `g_pGuildZone[].CityTax` *is* persisted (file rewrite) but is re-clamped on load (`CReadFiles.cpp:809-814`).

### 3.2 Detailed breakdown of the business rules

---

### Business Rule: BR-01 — Payload truncation and re-truncation

**Overview**
The handler guarantees a NUL-terminated string before any use of `m->String` by zeroing the two highest payload bytes twice: immediately on entry (`:24-25`) and again after the censoring stage (`:178-179`). Because `MESSAGE_LENGTH` is 96 (`Code/Basedef.h:129`), indices 94 and 95 are cleared.

**Detailed description**
The inbound structure is `MSG_MessageChat { _MSG; char String[MESSAGE_LENGTH]; }` (`Code/Basedef.h:1440-1444`) whose payload begins at byte offset 12 and ends at byte 107 (108 bytes total). The first normalization pass runs *before* the `USER_PLAY` gate, so even a packet from a non-playing session is sanitized — this is the only write the function performs on an unauthorized session, and it is done deliberately as a precondition for the `sscanf` at `:35`. Clearing both `String[95]` (the last valid byte) and `String[94]` costs one payload byte: the longest transmittable text is 94 characters plus the terminator. This is not documented anywhere and no constant expresses the off-by-one; the comment-free double assignment reads as a defensive habit copied from decompiled code, and the same idiom appears in `SendClientMessage` (`Code/TMSrv/SendFunc.cpp:41-42`), `CrackLog` (`Server.cpp:6688-6689`) and `SendGuildList` (`SendFunc.cpp:1290-1291` for `MobName`), i.e. it is a project-wide convention rather than a local decision.

The second pass exists because the function mutates the payload in the middle of its own execution: `strncpy(m->String, "??????", 6)` at `:174` writes six bytes with no terminator guarantee. The re-termination at `:178-179` re-establishes the invariant before the buffer is echoed to up to 1,088 sockets. In practice the second pass is what keeps the relay legal; removing it would allow a 96-byte non-terminated payload to be re-broadcast to clients.

The truncation is however *not* applied to `m->Size`, which is the field that governs how many bytes each recipient actually receives (`GridMulticast` → `AddMessage(msg, msg->Size)`, `SendFunc.cpp:966`). Consequently the guarantee "the payload is terminated" is only true for a reader that respects the 108-byte structure. A packet declaring `Size = 8000` will relay 8,000 bytes drawn from the receiving socket's buffer (`RECV_BUFFER_SIZE` = 128 KB, `Code/CPSock.h:44`), past the end of the 108-byte structure. Nothing in `CPSock::ReadMessage` (`Code/CPSock.cpp:397`) or `ProcessClientMessage` (`:42-64`) enforces per-type size equality, because `BASE_CheckPacket` returns `FALSE` unconditionally (`Code/Basedef.cpp:6585`).

**Rule workflow**
```
entry
  -> String[95] := 0 ; String[94] := 0
  -> ID := conn
  -> Mode gate
  -> command parse (sscanf)
  -> ... command branches (may return)
  -> BR censor may write 6 bytes without NUL
  -> String[95] := 0 ; String[94] := 0        (re-establish invariant)
  -> mute gate
  -> GridMulticast(payload, payload->Size)      (Size NOT normalized)
  -> ChatLog
```

### Business Rule: BR-02 — Server-authoritative sender identity stamping

**Overview**
`m->ID = conn` (`:27`) overwrites the packet's `ID` header field with the socket-derived connection index before the packet is relayed.

**Detailed description**
The `ID` field is the client's own view of "who is speaking": the receiving client uses it to resolve the speaker's sprite/name in the chat bubble. Because the handler relays *the same buffer* it received, leaving the client-supplied `ID` in place would let any player impersonate any other player in local chat — a classic ID-spoofing vulnerability in this protocol family. Overwriting with `conn` makes the field server-authoritative. This rule is the single most important security control in the component and it is applied **before** the session-state gate, so the stamping cannot be bypassed by an early return.

`conn` is trustworthy by construction: it originates from `GetUserFromSocket(wParam)` in the `WSA_READ` handler (`Server.cpp:3946`), which closes the socket when the lookup returns 0, so `conn ∈ [1, MAX_USER)`. The dispatcher's own bounds check is applied to the *client-supplied* `std->ID` (`ProcessClientMessage.cpp:42`) and therefore protects nothing about `conn` — the invariant is established upstream and assumed here, which is correct but undocumented.

The write is *not* protected by any invariant on `pMob[conn]`/`pUser[conn]` within the function; the function indexes `pUser[conn]` at `:29` and `pMob[conn]` at `:39` without a local bounds test. For a handler reachable from the network this is a latent hazard if any future caller passes an index outside `[1, MAX_USER)`; today the only caller guarantees it.

**Rule workflow**
```
client packet (ID = arbitrary, attacker-chosen)
  -> conn = GetUserFromSocket(wParam)  (server truth)
  -> Exec_MSG_MessageChat(conn, pMsg)
  -> m->ID := conn                     (overwrite before any relay)
  -> GridMulticast(...)                (recipients see ID = conn)
```

### Business Rule: BR-03 — In-game session gate

**Overview**
`if (pUser[conn].Mode != USER_PLAY) return;` (`:29-30`) restricts the entire component (commands *and* chat) to sessions that are fully in game.

**Detailed description**
`USER_PLAY` is 22 (`Code/TMSrv/CUser.h:36`). The full state set is `USER_EMPTY` 0, `USER_ACCEPT` 1, `USER_LOGIN` 2, `USER_SELCHAR` 11, `USER_CHARWAIT` 12, `USER_WAITDB` 13, `USER_PLAY` 22, `USER_SAVING4QUIT` 24 (`CUser.h:26-37`). Because the check is an equality against the only "playing" state, a character that is mid-logout (`USER_SAVING4QUIT`) or awaiting the DB confirmation (`USER_CHARWAIT`) cannot transmit chat — a deliberate restriction that also prevents the `guildtax` command from racing a character save.

The gate is silent: nothing is sent to the client and nothing is logged on the rejection path. Since the "correct" fallback exists later in the function (`:195-199`), this early importation of the same check makes the later branch dead code (BR-22), and an operator investigating a "chat does nothing" report sees no server-side evidence at all.

Because the gate is placed *after* `m->ID = conn` and both truncations but *before* `sscanf`, a non-playing session cannot reach the command parser, the tax writer, the file rewrite, or the audit sinks. This ordering is the effective authorization line for every privileged action in the file.

**Rule workflow**
```
Mode == USER_PLAY ?
  yes -> continue to command dispatch
  no  -> return (no client feedback, no log)
```

### Business Rule: BR-04 — Two-token command parsing

**Overview**
`sscanf(m->String, "%s %s", szCmd, szString)` (`:35`) splits the payload into a command token and one argument token, both in 256-byte stack buffers.

**Detailed description**
The two buffers `szCmd[256]` and `szString[256]` (`:32-33`) are far larger than the 96-byte payload, so the conversion itself cannot overflow them (the payload is terminated by BR-01 first). Only the first two whitespace-delimited fields are captured; anything after the second token is silently discarded, which is why `"guildtax 5 extra"` behaves identically to `"guildtax 5"`. There is no quoting, no escaping, and no case folding — matching is exact via `strcmp`, so `Guildon`, `GUILDON` and `guildtax ` (trailing space) are all treated as ordinary chat text and broadcast to the grid.

The critical weakness is the missing initialization of both buffers. If the payload begins with whitespace, `sscanf` may assign nothing to `szCmd`, leaving it uninitialized; if the payload contains a single token, `szString` is never written. `szCmd` is then compared against all nine literals with `strcmp` — reading uninitialized stack memory — and, for `guildtax`, `atoi(szString)` (`:74`) converts garbage into a candidate tax value. The validation at `:76` partially mitigates this (garbage that parses to a negative number or > 30 is rejected, and a `0` result is rejected unless the first byte is `'0'`), but garbage that happens to parse into `1..30` **passes** and is written into `g_pGuildZone[i].CityTax` and persisted to disk. Whether this is reachable in practice depends on uninitialized stack contents, i.e. it is non-deterministic rather than impossible; it is a defect regardless of exploitability.

A second consequence is that the command namespace is not separated from the chat namespace: a player who types "guild" as a normal word triggers the roster panel instead of speaking, and there is no escape prefix. Any client-side chat feature that can emit a leading `guildon`, `whisper`, etc. will collide with the server command set.

**Rule workflow**
```
String -> sscanf("%s %s")
  token1 -> szCmd   (may stay uninitialized if payload starts with space)
  token2 -> szString (stays uninitialized if payload has 1 token)
  exact strcmp chain against 9 literals
  no match -> fall through to broadcast as ordinary chat
```

### Business Rule: BR-05 — `guildon` restores guild identity

**Overview**
`guildon` clears `pMob[conn].GuildDisable` (only if it is currently 1), re-sends the player's score block and signals the client that the flag is now 0 (`:37-48`).

**Detailed description**
`GuildDisable` is an `int` on the mob object (`Code/TMSrv/CMob.h:76`), initialized to 0 in `CMob`'s constructor (`CMob.cpp:37`), reset to 0 at character login (`ProcessDBMessage.cpp:913`) and never persisted. Its semantics are "pretend this character has no guild": it is consulted when the guild tag is rendered into score/create-mob packets (`GetFunc.cpp:990-994`, `:1114-1115`), when guild-based PvP targeting is resolved (`GetFunc.cpp:1549-1551`), when damage is attributed (`_MSG_Attack.cpp:375-383`), by the score push (`SendFunc.cpp:1173-1174`) and by the war/coliseum target validators (`ProcessSecMinTimer.cpp:1607-1611`, `Server.cpp:4546-4550`, `4823-4828`, `4935-4940`, `5132-5137`, `5244-5249`). It is therefore a *guild-identity masking* switch used to make a player untargetable/untagged by guild logic during events, not a chat setting.

The command is idempotent: the state change, the score push and the client signal all occur only when `GuildDisable == 1`. If the flag is already 0 the command is a silent no-op — no acknowledgement, no error. The exact-equality test (`== 1`) rather than a truth test means a hypothetical value of 2 would make the command permanently ineffective; no writer in the codebase produces such a value, so this is latent, not active.

The feedback is split across two channels: `SendScore(conn)` (`SendFunc.cpp:1136`) pushes the full `MSG_UpdateScore` (which itself zeroes the guild fields when `GuildDisable` is set, `SendFunc.cpp:1173`) and `SendClientSignalParm(conn, ESCENE_FIELD, _MSG_GuildDisable, 0)` pushes `MSG_STANDARDPARM` with `Type = 164 | 0x300 = 868` and `ID = 30000`. The client needs both: the score block to repaint the name/guild area and the parm signal to update its own internal "guild visible" toggle. Omitting either would leave the client stale, which is why the two calls are always paired in both branches.

**Rule workflow**
```
GuildDisable == 1 ?
  yes -> GuildDisable := 0
         SendScore(conn)
         SendClientSignalParm(conn, ESCENE_FIELD, _MSG_GuildDisable, 0)
  no  -> nothing
return (never falls through to chat)
```

### Business Rule: BR-06 — `guildoff` hides guild identity

**Overview**
`guildoff` sets `pMob[conn].GuildDisable = 1` when it is currently 0, re-sends the score block and signals the client with parm `1` (`:50-61`).

**Detailed description**
This is the mirror of BR-05 and the operationally interesting half: it is the only way a player can enter "no guild tag / no guild targeting" state, which is a competitive advantage inside guild wars and the coliseum. There is no rank restriction, no cooldown, no cost and no confirmation, so any in-game character can toggle it at will; the effect is cleared only by the player himself, by logout (`ProcessDBMessage.cpp:913`) or by a client relog (since it is not persisted).

Because the flag feeds both rendering (`GetFunc.cpp` create-mob/score) and combat legality (`_MSG_Attack.cpp:375-383`, where the attacking guild id is replaced by 0 when the flag is set, changing the friendly-fire decision), toggling it mid-fight changes PvP outcomes. The component performs no re-validation of combat state before applying the change: a player can issue `guildoff` at any moment the session is `USER_PLAY`, including between two attack packets.

The acknowledgement path is identical to BR-05 but with parm 1, and the score push reflects the masked state because `SendScore` consults the same flag (`SendFunc.cpp:1173`). Note the round trip: the player's own client learns the new state from the score block, while each *other* client learns it only when the next create-mob/score refresh for this player is generated — the handler does not broadcast the change to the grid.

**Rule workflow**
```
GuildDisable == 0 ?
  yes -> GuildDisable := 1
         SendScore(conn)                       (now renders guild = 0)
         SendClientSignalParm(..., _MSG_GuildDisable, 1)
  no  -> nothing
return
```

### Business Rule: BR-07 — `guildtax` authorization (rank 9)

**Overview**
The tax command is refused unless `pMob[conn].MOB.GuildLevel == 9` (`:64-65`), the guild-master rank.

**Detailed description**
`GuildLevel` lives in `STRUCT_MOB` (`Code/Basedef.h:474`, "used to define if it's a guild member or leader"). The comparison is an exact equality against the literal `9`, with no named constant. Because the check is exact, any other rank encoding — including a higher administrative rank if one existed — cannot use the command. The refusal is silent: no message, no log, and the function returns immediately without falling through to chat, so a non-leader typing `guildtax 10` sees absolutely nothing (not even their own text being spoken).

`GuildLevel` is character data loaded by DBSrv and mirrored into `pMob[conn].MOB`, so the authority for the rank is the persisted character record, not the session. A player cannot forge it through this packet because the handler never reads `GuildLevel` from the payload.

Note the authorization is *rank-only*: it does not verify that the player is actually the leader of an existing, charged guild (that comes from BR-08's `ChargeGuild` match), does not check for the actual guild-tax permission flag (none exists), and does not verify the guild is not disbanding. Two separate checks are therefore required to be able to change a tax: rank 9 *and* ownership of a zone.

**Rule workflow**
```
GuildLevel == 9 ?
  yes -> continue to zone resolution (BR-08)
  no  -> return silently (no client feedback, no audit)
```

### Business Rule: BR-08 — `guildtax` zone resolution (first `ChargeGuild` match)

**Overview**
The handler scans `g_pGuildZone[0..MAX_GUILDZONE-1]` (5 zones) and acts on the **first** entry whose `ChargeGuild` equals the player's `MOB.Guild` (`:67-72`, `:99`).

**Detailed description**
`g_pGuildZone` is `STRUCT_GUILDZONE g_pGuildZone[MAX_GUILDZONE]` (`Code/Basedef.h:2441`), persisted in `Guild.txt`. `ChargeGuild` is the guild that currently holds (charges) a city; it is written by the castle/coliseum logic (`Server.cpp:6200`, where zone 4 mirrors zone 0) and by the guild file loader. The player's guild id is read from `pMob[conn].MOB.Guild` (`:67`) — again persisted character data, not client input.

Two behaviours follow from the "first match" semantics. First, a guild that holds **two** zones can only ever adjust the lower-indexed one; the higher-indexed zone is unreachable through this command, and since `break` exits the loop on the first successful write (`:99`), no iteration over multiple owned zones occurs. Second, a guild that holds **no** zone gets a completely silent no-op: the loop completes without matching, and the `return` at `:101` fires. Combined with BR-07's silent refusal, the command has three distinct silent-failure modes (not rank 9, no owned zone, invalid value — the last one at least emits `_NN_Guild_Tax_0_to_30`).

The zone index `i` is also the index used by the latch `TaxChanged[i]` and by the outbound acknowledgement, so the correlation between the five zones and the five latch slots is positional and implicit; nothing validates that the latch array and the zone array stay in sync if `MAX_GUILDZONE` ever changes in one place only.

**Rule workflow**
```
Guild := pMob[conn].MOB.Guild
for i in 0..4:
    if g_pGuildZone[i].ChargeGuild != Guild: continue
    -> BR-09 validation
    -> BR-10 latch
    -> BR-11 apply + notify + persist
    -> BR-12 audit
    -> break              (only the first matching zone is ever touched)
(no match) -> return silently
```

### Business Rule: BR-09 — `guildtax` value validation (`0..30`, ASCII-`'0'` probe)

**Overview**
`int tax = atoi(szString); if (tax < 0 || tax > 30 || szString[0] != 48 && !tax)` rejects the value unless it is an integer in `[0,30]` and, when it parses to zero, literally starts with the character `'0'` (`:74-80`).

**Detailed description**
`atoi` returns 0 both for the string `"0"` and for any unparsable text, so the third clause is a heuristic to distinguish "the player asked for 0%" from "the player typed something that is not a number". Because `&&` binds tighter than `||`, the condition is `(tax < 0) || (tax > 30) || ((szString[0] != 48) && (tax == 0))`, which is the intended grouping. The literal `48` is the ASCII code of `'0'` written as a magic number rather than the character constant. The heuristic has three holes: `"0abc"` is accepted as 0; a payload with **no second token at all** feeds an *uninitialized* `szString` into `atoi` (see BR-04), so the result is non-deterministic; and `"+5"`, `" 5"`, `"5%"` are all accepted because `atoi` silently tolerates junk suffixes.

On rejection the handler sends `g_pMessageStringTable[_NN_Guild_Tax_0_to_30]` (`Language.h:188` → index 168) and `break`s out of the zone loop, then returns. The message text itself lives in `Language.txt`, which is not in the repository, so the exact wording cannot be verified; the macro name states the intended contract ("0 to 30").

The upper bound is a genuine cross-component inconsistency. The guild-file loader clamps a loaded `CityTax` to `[0,20]` and substitutes `10` when outside (`CReadFiles.cpp:809-814`), while this command accepts up to `30` and writes it directly (`:88`). A guild that sets 25-30% therefore keeps it until the next restart, at which point the loader silently resets it to 10%. Downstream consumers also disagree: `_MSG_Buy.cpp:109` treats `CityTax >= 30` as "no tax", so a 30% setting (explicitly accepted here) is charged as 0% while `SendShopList` still advertises 30.

**Rule workflow**
```
tax := atoi(szString)
if (tax < 0)                                     -> reject ("0 to 30") ; break
if (tax > 30)                                    -> reject ("0 to 30") ; break
if (szString[0] != '0' && tax == 0)              -> reject ("0 to 30") ; break
accept -> BR-10
```

### Business Rule: BR-10 — One change per latch cycle

**Overview**
If `TaxChanged[i] == 1` the command is refused with `g_pMessageStringTable[_NN_Only_Once_Per_Day]` (`Language.h:194` → index 174) (`:82-86`).

**Detailed description**
`TaxChanged[MAX_GUILDZONE]` (`Server.cpp:436`, `Server.h:384`) is a process-wide, non-persisted latch per zone, zero-initialized at startup. It is set to 1 on a successful change (`:89`) and cleared in exactly one place: the Colosseum state machine, when a coliseum cycle finishes (`ColoState == 8 → 0`, `Server.cpp:6404-6407`, iterating all five zones). It is *not* cleared by a day boundary, so the player-facing message "Only Once Per Day" does not describe the implemented rule. If the coliseum runs more than once a day the tax may be changed more than once a day; if it never runs, the tax is frozen for the process lifetime.

The check is ordered **after** value validation (BR-09) and **before** application (BR-11), so an invalid value never consumes the latch and a latched zone still receives the informative range error rather than the "already changed" error when both conditions hold. This ordering is the only reason the error messages are meaningful.

Because the latch is per-zone and process-wide, it is unaffected by the player logging out, changing characters, or the guild changing hands: a new guild master inheriting a charged zone within the same cycle cannot set the tax, and the message they receive is misleading. The latch is also not guarded by any lock or ownership check — it is written from the network thread only, which happens to be the single server message loop, so there is no race today, but the invariant is implicit.

**Rule workflow**
```
TaxChanged[i] == 1 ?
  yes -> SendClientMessage(_NN_Only_Once_Per_Day) ; break ; return
  no  -> apply (BR-11) and set TaxChanged[i] := 1
```

### Business Rule: BR-11 — Tax application, acknowledgement and persistence

**Overview**
On success the handler writes `g_pGuildZone[i].CityTax = tax`, latches the zone, renders an acknowledgement from `g_pMessageStringTable[169]` with `(tax, 0)` and rewrites `Guild.txt` through `CReadFiles::WriteGuild()` (`:88-94`).

**Detailed description**
The in-memory write is effective immediately for every consumer of `g_pGuildZone[].CityTax`: shop pricing and tax revenue in `_MSG_Buy.cpp`/`_MSG_Sell.cpp`, and the client-facing shop list. Persistence is synchronous and unconditional: `CReadFiles::WriteGuild()` (`CReadFiles.cpp:827`) reopens the zone-parameterized path (`GUILD_PATH` formatted with `ServerGroup`/`ServerIndex`), falls back to a local `Guild.txt` on failure, writes all five zones' `ChargeGuild`, `ChallangeGuild`, `CityTax`, `Clan` and `Victory` lines, and only logs on a total failure to open. It returns `void`, so the handler cannot distinguish success from a failed flush — the player is told the change succeeded even when the file could not be written, and the value survives only in RAM until the next save.

The acknowledgement uses a **hard-coded literal index 169** rather than the available constant `_DD_Set_Guild_Tax 169` (`Language.h:189`), and passes the string-table entry itself as the format string with two arguments `(tax, 0)`. The second argument is a hard-coded `0`, which suggests the original message template carries a second conversion the developer did not want to fill meaningfully (most likely a guild name or a "previous value" slot). Serving a data-file string as a format is a code smell with a real failure mode: a malformed `Language.txt` line containing `%s`/`%n` would be executed by the server process, and the arity mismatch (`(tax, 0)` against an unknown number of conversions) is unchecked.

The whole persistence step is a *side effect inside a network handler*: a drop of an attacker-influenced file write into the hot path of a chat packet. It happens at most once per cycle per zone thanks to BR-10, which bounds the I/O amplification, but it makes the chat handler a file-writer and thereby couples the chat surface to disk health and to the `Guild.txt` format.

**Rule workflow**
```
g_pGuildZone[i].CityTax := tax
TaxChanged[i] := 1
sprintf(temp, g_pMessageStringTable[169], tax, 0)
SendClientMessage(conn, temp)
CReadFiles::WriteGuild()          (rewrite Guild.txt; result ignored)
-> BR-12 audit
```

### Business Rule: BR-12 — Tax-change audit trail

**Overview**
After a successful change the raw command text is logged as `sys,<raw payload>` with the account name and IP (`:96-97`).

**Detailed description**
`Log()` (`Server.cpp:6701`) prefixes a timestamp and, when the IP argument is non-zero, the dotted-quad form of `pUser[conn].IP`, then writes to the main log file and mirrors the line to the server window title (`SetWindowTextA`). Using the *raw* payload (`m->String`) rather than the normalized values means the audit record preserves exactly what the operator typed, including any trailing tokens that were ignored by `sscanf` — useful forensically, and also the vehicle for the format-string defect described in BR-23, since the payload reaches `fprintf` as a format.

The prefix `"sys,"` is a log-severity convention used across the server (`Log("sys,GuildName initialized", ...)`, `Server.cpp:6215`) that lets operators grep for administrative events. The account and IP are passed positionally as `(char*, unsigned int)`; `Log`'s third parameter is `unsigned int ip`, and `pUser[conn].IP` is stored as `S_un.S_addr` in network order (`CUser::AcceptUser`, `CUser.cpp:72`), so the printed octets are reversed relative to the conventional dotted-quad.

No audit is written for *rejected* tax attempts, for `guildon`/`guildoff`, or for the flag toggles. From an operations standpoint the only privileged action with an audit trail is the tax change; identity masking and channel opt-outs, which materially change PvP legality and communication availability, are invisible in the logs.

**Rule workflow**
```
sprintf(temp, "sys,%s", m->String)
Log(temp, pUser[conn].AccountName, pUser[conn].IP)
   -> timestamp + IP prefix
   -> fprintf(fLogFile, LogTemp)     <-- LogTemp used as format string
   -> SetWindowText(hWndMain, LogTemp)
```

### Business Rule: BR-13 — `guild` roster request

**Overview**
`guild` calls `SendGuildList(conn)` and returns; guildless players get nothing (`:104-108`).

**Detailed description**
`SendGuildList` (`SendFunc.cpp:1259`) returns immediately when `pMob[conn].MOB.Guild <= 0` (`:1263-1264`), which is where the "no guild" case is handled — the handler itself performs no check, so the silence is delegated. For a guilded player the function walks all 1,000 sessions, filters on `Mode == USER_PLAY` and matching `MOB.Guild`, and emits the member list in `MSG_MessagePanel` chunks of roughly 70 characters (`max_size = 70`) so each panel stays inside the 96-byte `MESSAGE_LENGTH` limit.

This is the only command in the component that performs a full `MAX_USER` scan from within the chat handler, so its cost is O(1,000) per invocation with no cooldown and no rate limit. Combined with BR-24 (no throughput control) it is a cheap way for a single client to force 1,000-iteration scans in a tight loop — a small but real CPU amplification surface on the single-threaded message loop.

The command is also reachable by typing the plain word "guild" in chat, which means normal conversation about guilds silently opens a roster panel instead of speaking, and the text is consumed (the function returns before the broadcast at `:193`).

**Rule workflow**
```
SendGuildList(conn)
  -> Guild <= 0 ? return (silent)
  -> scan 1..MAX_USER, collect names of same-guild USER_PLAY sessions
  -> flush MSG_MessagePanel chunks at ~70 chars
return (no chat broadcast)
```

### Business Rule: BR-14 — `whisper` channel toggle

**Overview**
`whisper` flips `pUser[conn].Whisper` (`0 ↔ 1`) and reports the *new* state inverted: value 1 is reported as `"Whisper : Off"`, value 0 as `"Whisper : On"` (`:111-121`).

**Detailed description**
The assignment `pUser[conn].Whisper = pUser[conn].Whisper == 0` is a normalization as much as a toggle: any non-zero value becomes 0, and 0 becomes 1. The flag's meaning is "blocking enabled", not "channel enabled", which is why the reporting is inverted; a reader who assumes the field means "whisper on" will misread every consumer. Four consumers exist: the whisper handler refuses delivery when the *recipient* has the flag set and the sender's level is below 1,000 (`_MSG_MessageWhisper.cpp:1320`), `_MSG_Trade.cpp:130` blocks trade invitations when either party has it set, `_MSG_ReqRanking.cpp:30` suppresses something equivalent for the target, and `SendFunc.cpp` uses it in the private channel paths. The GM level exemption at 1,000 means staff can always whisper regardless of the flag — an implicit privilege rule that lives outside this component.

The flag is `int` on `CUser` (`CUser.h:84`) and has no persistence: it is reset to 0 by the account-login handler (`ProcessDBMessage.cpp:387`) and is not part of the character record, so every relog silently re-enables whispers. The `CUser` constructor does not initialize it explicitly (`CUser.cpp:22-42`); the zero value comes from static initialization of the `pUser` array, which makes the default state dependent on the global-object initialization order rather than on an explicit contract.

The player-facing strings `"Whisper : Off"` / `"Whisper : On"` are hard-coded English literals, unlike almost every other message in the server, which comes from `g_pMessageStringTable` / `Language.txt`. This is a localization regression and also means the response cannot be reworded without a recompile; the same applies to the four sibling toggles.

**Rule workflow**
```
Whisper := (Whisper == 0) ? 1 : 0
Whisper == 1 ? SendClientMessage("Whisper : Off")
             : SendClientMessage("Whisper : On")
return
```

### Business Rule: BR-15 — `partychat` channel toggle

**Overview**
`partychat` flips `pUser[conn].PartyChat` and reports `"Party Chatting : Off"` when the result is 1 (`:123-133`).

**Detailed description**
`PartyChat` (`CUser.h:86`) is the party-channel opt-out. Its consumers are `PartyGridMulticast`, which skips recipients whose flag is set (`SendFunc.cpp:1016`) and refuses to operate when the party leader has it set (`:1042`), plus the party broadcast in `_MSG_MessageWhisper.cpp:1216`. The semantics are therefore "do not deliver party chat to me", and — because `:1042` gates on the *leader* — a leader who opts out effectively disables the party channel for the whole group, an unintended escalation that a player cannot detect from the "Off" confirmation.

Like BR-14 the toggle normalizes any non-zero value to 0, is session-scoped (`ProcessDBMessage.cpp:389` resets it at login), and uses an inverted human-readable report. It is one of the five flags written *only* by this component; the whisper component reads four of them but never writes any, which establishes a clean one-writer/many-readers contract for the flag set.

Because party chat delivery is a different opcode (`_MSG_MessageWhisper`), this handler never verifies that the player is actually in a party before advertising the state. A solo player can set the flag and receive a confirmation that is operationally meaningless until they join a group — a UX inconsistency, not a logic error.

**Rule workflow**
```
PartyChat := (PartyChat == 0) ? 1 : 0
PartyChat == 1 ? SendClientMessage("Party Chatting : Off")
               : SendClientMessage("Party Chatting : On")
return
```

### Business Rule: BR-18 — `chatting` toggle (orphan flag)

**Overview**
`chatting` flips `pUser[conn].Chatting` and reports `"Chatting : Off"` when the result is 1 (`:159-169`), but no code in the repository ever reads the flag.

**Detailed description**
`Chatting` exists on `CUser` with the comment `//2648 Chatting??` (`CUser.h:87`) — the decompiler could not determine its purpose, and the `??` is preserved in the source. A repository-wide search for reads of `pUser[...].Chatting` returns only the writes in this handler, the reset at `ProcessDBMessage.cpp:392`, and the constructor's absence of initialization. The other four flags all have identifiable consumers (BR-14..BR-17), so this one is genuinely dead.

The intended meaning is unmistakable from the message text: a global "do not show me any chat" opt-out, i.e. the local-channel equivalent of the other four. It is not wired into `GridMulticast`, which does not inspect any `CUser` field (`SendFunc.cpp:959-967` adds the message to every non-empty grid occupant). The consequence is that the local channel — the only channel a player cannot escape — is exactly the channel whose opt-out is unimplemented, and the client will happily display "Chatting : Off" while continuing to receive every local message.

This rule is therefore a *declared but unenforced* business rule: the user-visible contract exists (a toggle with confirmation), the enforcement does not. Anyone reading the toggle implementation in isolation would conclude local chat is filterable.

```
Chatting := (Chatting == 0) ? 1 : 0

              : SendClientMessage("Chatting : On")

   (no consumer; local broadcast ignores the flag)
```

### Business Rule: BR-19 — Event-area chat censorship

**Overview**
While a BR ("britem") event is running (`BrState != 0 && BRItem > 0`), any chat emitted from inside one of two hard-coded rectangles has its first six characters replaced by `"??????"` (`:171-176`).

**Detailed description**
The rectangles are `X 2604..2648, Y 1708..1744` — the coliseum arena used by the BR event (`Server.cpp:6338`, `_MSG_Attack.cpp:386`, `_MSG_AcceptParty.cpp:98`) — and `X 896..1150, Y 1405..1538`, an area where the server forcibly re-skins players into a fixed appearance (`SendFunc.cpp:898-914`, items 3505 and 3999). Both are event/PvP areas where the operator wants to suppress tactical communication. The condition uses the operator precedence `A && B && C && D || E && F && G && H`, which parses as `(A&&B&&C&&D) || (E&&F&&G&&H)` — the intended grouping — and reads the **server-side** `pMob[conn].TargetX/TargetY`, so a client cannot spoof its position to escape the censor.

The mechanism itself is broken. `strncpy(m->String, "??????", 6)` copies exactly six bytes; `strncpy` only pads with NULs when the source is *shorter* than the count, and here the source length equals the count, so no terminator is written. Characters 6..n of the original message therefore remain in the buffer and are relayed unchanged (the re-termination at `:178-179` only touches bytes 94 and 95). A 20-character message leaves 14 readable characters; a 94-character message leaves 88. The censor masks a prefix, not the message. It is only effective for messages of six characters or fewer.

Secondary characteristics: the check is applied *after* all command branches, so event participants can still emit commands (with their argument text) from inside the censored area; it is applied *before* the mute gate, so a muted player's text is censored and then discarded; and the replacement is a fixed six-character literal with no message-table entry, no localization and no configurability.

**Rule workflow**
```
BrState != 0 && conn < MAX_USER && BRItem > 0 ?
  inside rect A (2604..2648 x 1708..1744) or rect B (896..1150 x 1405..1538) ?
    -> strncpy(String, "??????", 6)     (chars 6..n preserved)
  -> continue
-> re-terminate String[95], String[94]
-> mute gate -> broadcast
```

### Business Rule: BR-20 — `MuteChat` gate

**Overview**
`if (pUser[conn].MuteChat == 1)` sends `g_pMessageStringTable[_NN_No_Speak]` (index 353) and returns without broadcasting (`:181-185`).

**Detailed description**
`MuteChat` is an administrative sanction, not a player preference: it is toggled by the console `mute <name>` command, forced on by `muteall` and cleared by `desmuteall` (`Code/TMSrv/imple.cpp:1524-1559`). It defaults to 0 in the `CUser` constructor (`CUser.cpp:36`) and is applied identically by the whisper handler (`_MSG_MessageWhisper.cpp:100` and `:1129`), so the sanction covers local and private chat consistently.

The gate is placed **after** the nine command branches, which means a muted player can still run `guildon`, `guildoff`, `guildtax`, `guild` and all five toggles, and can still cause a `Guild.txt` rewrite. Whether that is intended is not documented; it is certainly an asymmetry between "speech" and "commands" that the same packet carries. The gate is also after the BR censor, so an event-area message is censored first and discarded second — harmless, but it shows the ordering is incidental rather than designed.

The test is an exact `== 1` rather than a truth test. Both administrative writers set exactly 0 or 1, so the behaviour is correct today; any future writer storing 2 would silently un-mute the player. There is no announcement to the grid that a player is muted, no log entry when a blocked message is discarded, and no expiry — the sanction persists for the session only, because `MuteChat` is not part of the character record (it is not saved by `SaveUser`, `Server.cpp:7056-7083`), so a relog lifts it.

**Rule workflow**
```
MuteChat == 1 ?
  yes -> SendClientMessage(conn, _NN_No_Speak)
         return (message not relayed, not audited)
  no  -> GridMulticast (BR-21) + ChatLog (BR-23)
```

### Business Rule: BR-21 — Local broadcast topology and sender exclusion

**Overview**
The message is delivered with `GridMulticast(pMob[conn].TargetX, pMob[conn].TargetY, (MSG_STANDARD*)pMsg, conn)` (`:193`), i.e. to every occupied cell of a 33x33 window centred on the sender, except the sender (`:187-194`).

**Detailed description**
The overload resolved here is `GridMulticast(int tx, int ty, MSG_STANDARD *msg, int skip)` (`SendFunc.cpp:843`) — not the `(conn, tx, ty, msg)` overload at `:620`; the pointer in the third position selects it. The window is `VIEWGRIDX/VIEWGRIDY = 33`, `HALFGRIDX/HALFGRIDY = 16` (`Basedef.h:95-101`), clipped against `MAX_GRIDX/MAX_GRIDY = 4096` and against negative starts. Delivery requires `tmob > 0`, `tmob != skip`, `pMob[tmob].Mode != MOB_EMPTY`, `msg != NULL` and `tmob < MAX_USER` (`SendFunc.cpp:884-966`); the payload is queued with `pUser[tmob].cSock.AddMessage((char*)msg, msg->Size)`. The theoretical maximum is 33*33-1 = 1,088 recipients per chat line at one message each.

The sender is excluded because `skip == conn`; the client is expected to echo its own message locally. There is no verification that the sender's `TargetX/TargetY` is a valid grid coordinate, and this overload does not relocate the sender into its own grid the way the `(conn, tx, ty, msg)` overload does (`:629-657`) — it only reads the grid. The coordinates come from server state, so the sender cannot choose the broadcast centre, but a stale/desynced position would broadcast to the wrong place rather than erroring.

Two structural consequences matter. First, the *same buffer* is queued for every recipient (no per-recipient copy), so any later mutation of the inbound buffer would corrupt all pending sends — the handler performs no mutation after this call, which is the only thing keeping it safe. Second, `AddMessage` writes `pSMsg->Size = Size` into that shared buffer for every recipient (`CPSock.cpp:533`), i.e. the packet header is rewritten 1,088 times with the same value; the return value is ignored, so when a recipient's 128 KB send buffer is full (`CPSock.cpp:519-525`) the message is dropped with only a log line, and the sender is never told.

**Rule workflow**
```
tx,ty := pMob[conn].TargetX/TargetY
window := [tx-16 .. tx+16] x [ty-16 .. ty+16] clipped to [0,4095]
for each occupied cell:
    tmob != 0, tmob != conn, Mode != MOB_EMPTY, tmob < MAX_USER
      -> pUser[tmob].cSock.AddMessage(pMsg, pMsg->Size)
(sender excluded; client echoes locally)
```

### Business Rule: BR-22 — Unreachable "wrong status" fallback

**Overview**
The `else` branch at `:195-199` sends `"DEBUG:Client send chatting message with wrong status"` and logs `"err,send chatting message with wrong status"`, but it can never execute.

**Detailed description**
The function returns at `:29-30` when `Mode != USER_PLAY`, and every command branch returns before `:187`. Consequently the condition `if (pUser[conn].Mode == USER_PLAY)` at `:187` is always true when reached, and the `else` is dead. The decompiler evidently reconstructed the original's two-path structure without collapsing it after the early gate was introduced.

The dead branch documents the *intended* behaviour: an explicit client-visible diagnostic plus an operator log for a malformed session state. In the live code the same situation is silent. This is worth recording as a business-rule contradiction rather than a mere code smell: the component declares an error-handling contract that it does not honour, and the only trace of a bad-state chat packet is the absence of any log entry.

The nearby `int leader = pMob[conn].Leader; if (!leader) leader = conn;` (`:189-191`) is the second dead artifact: `leader` is computed (and would have been used to centre the broadcast on the party leader, as `PartyGridMulticast` does with `Leaderconn`, `SendFunc.cpp:985`) but the broadcast at `:193` uses `conn` and the local variable is never read. The `-W3` build level (`TMSrv.vcxproj:59`) would emit an unused-variable warning for it; the project targets "no compile warnings" per the README, and this file still carries one.

**Rule workflow**
```
:187 if (Mode == USER_PLAY)  --> always true here
        GridMulticast(...)
     else                    --> unreachable
        SendClientMessage("DEBUG:Client send chatting message with wrong status")
        Log("err,send chatting message with wrong status", ...)
```

### Business Rule: BR-23 — Chat audit trail and its format-string exposure

**Overview**
Every relayed message produces `sprintf(temp, "chat, %s : %s", pMob[conn].MOB.MobName, m->String)` followed by `ChatLog(temp, pUser[conn].AccountName, pUser[conn].IP)` (`:201-202`).

**Detailed description**
The chat log is a separate sink from the main log: `ChatLog` (`Server.cpp:9225`) formats a date stamp plus IP and appends one line per message to `fChatLogFile`, opened by `StartChatLog` (`:9208`) as `.\chat_log\TM_<dd>_<mm>_<yyyy>_<hh>_<mm>_<ss>.txt` and rotated by the minute timer when the calendar day changes (`ProcessSecMinTimer.cpp:2030-2032`). Each line carries the character name (from `MOB.MobName`), the message body, the account name and the IP, which makes the log a full communication record — and a privacy-relevant data store, since it is written unconditionally for every chat line with no retention policy in code.

The critical defect is at the last step of both sinks: `sprintf(LogTemp, "%s %s %s \n", LogTemp, str2, str1);` followed by `fprintf(fChatLogFile, LogTemp);` (`Server.cpp:9241`,`9244`; identical shape in `Log`, `Server.cpp:6720`,`6723`). `LogTemp` is not a literal, so the *data* becomes the format string. A message containing `%n` reaches `fprintf` as a conversion specification, and `fprintf` will consume arguments from the stack that the caller never supplied. This is a remotely reachable, unauthenticated (any in-game player) write primitive in a 32-bit process, and it is exercised by the most mundane user action in the game. `_CRT_SECURE_NO_WARNINGS` (`TMSrv.vcxproj:61,79`) suppresses the one compiler diagnostic that would have flagged the printf-family misuse.

Two further defects live in the same formatting idiom: `sprintf(LogTemp, "%s ...", LogTemp, ...)` passes the destination buffer as its own source, which is undefined behaviour for overlapping objects (in practice the IP/timestamp prefix can be truncated or corrupted when the expansion outgrows the existing content); and `Log`/`ChatLog` share the global `temp[4096]` with this handler, so any future reorganisation that defers logging would interleave buffers.

The audit is also *conditional on success*: blocked messages (mute, BR-censored text is logged post-censor, command branches) never reach the chat log, so the record is of what was spoken, not of what was attempted, and `guildon`/`guildoff`/toggles leave no chat-log trace at all.

**Rule workflow**
```
accepted and relayed message
  -> sprintf(temp, "chat, %s : %s", MobName, String)
  -> ChatLog(temp, AccountName, IP)
       -> sprintf(LogTemp, "<stamp>")            (safe, literal)
       -> sprintf(LogTemp, "%s %s %s \n", LogTemp, account, temp)   (overlap)
       -> fprintf(fChatLogFile, LogTemp)          (LogTemp as FORMAT -> %n/%s hazard)
```

### Business Rule: BR-24 — Absence of throughput control (flood / filter)

**Overview**
The component implements no rate limiting, no duplicate suppression, no minimum interval, no per-player ignore list, no profanity/keyword filter and no maximum-length policy beyond the structural 96-byte payload.

**Detailed description**
Nothing in the inbound path paces chat: `CPSock::ReadMessage` drains every complete packet in a `while(1)` loop (`Server.cpp:3975-4005`), `ProcessClientMessage` performs only a `LastReceiveTime` refresh (`:56-57`), and this handler has no timestamp, counter or token bucket. `CUser::LastChat[16]` looks like it might be a throttle but is in fact the "last whisper correspondent" name cache used by reply addressing (`_MSG_MessageWhisper.cpp:1295-1368`, reset at `ProcessDBMessage.cpp:820`). The consequence is unbounded amplification: one small request produces up to 1,088 outbound queue writes, so a client that sends chat at line rate multiplies its bandwidth by roughly three orders of magnitude at the recipients and can fill their 128 KB send buffers (`CPSock.cpp:519-525`), which the handler cannot observe because `AddMessage`'s `FALSE` return is discarded by `GridMulticast`.

Content policy is limited to BR-19's six-character prefix mask inside two rectangles. There is no filtering of the message body outside events, no character validation (any byte except NUL reaches clients, since the payload is relayed raw), and no enforcement that the text is printable — the server is a byte-transparent relay for a 96-byte field. Combined with `Size` being client-controlled (BR-01), the relayed frame's declared length is also outside the handler's control.

This absence is itself the component's most consequential business rule for operations: because the local channel is unfilterable (BR-18) and unpaced (BR-24), the only levers an operator has against a chat abuser are the two administrative commands behind `MuteChat` (`imple.cpp:1524-1559`), which are console-only and session-scoped.

**Rule workflow**
```
inbound packet  -> no interval check -> no size check -> no content check
                -> up to 1,088 AddMessage calls
                -> audit write
(no throttle state is read or written anywhere in the path)
```

### Business Rule: BR-25 — Flag lifetime and reset

**Overview**
All five chat flags (`Whisper`, `PartyChat`, `KingChat`, `Guildchat`, `Chatting`) plus `GuildDisable` are runtime session state; they are written here, reset at account login, and never persisted.

**Detailed description**
The flags live on `CUser` (`CUser.h:84-87,106-107`) and `CMob` (`CMob.h:76`), neither of which is serialized by `SaveUser` (`Server.cpp:7056-7083` saves `STRUCT_MOB`, cargo, coin, donate, short skills, affects). The account-login completion path explicitly zeroes all of them (`ProcessDBMessage.cpp:387-392` for the chat flags, `:913` for `GuildDisable`), which is the authoritative reset point; the constructors do not set them (`CUser.cpp:22-42`, `CMob.cpp:37` for `GuildDisable` only), so first-use values come from static zero-initialization.

The practical rule for players is therefore: every opt-out and every guild-identity masking choice survives only until the next relog, and every character on the same account inherits nothing from the previous session because the reset happens per session slot rather than per character. For operators this means a "please turn off guild chat" request cannot be satisfied persistently, and a player who masks their guild to avoid PvP targeting must reapply the mask after every reconnect.

`TaxChanged` is a further lifetime layer: process-scoped, cleared only at the end of a coliseum cycle (BR-10), and lost entirely on restart while `CityTax` survives on disk. The two therefore have different lifetimes (queue latch vs. persisted value), which is the root cause of the "Only Once Per Day" message being wrong.

**Rule workflow**
```
session accept      -> flags zero (static init)
account login OK    -> flags := 0                        (ProcessDBMessage.cpp:387-392)
in-game             -> flags written ONLY by _MSG_MessageChat
character login     -> GuildDisable := 0                 (ProcessDBMessage.cpp:913)
logout / relog      -> nothing persisted -> session state lost
server restart      -> CityTax restored from Guild.txt (0..20 clamp), TaxChanged := 0
coliseum cycle end  -> TaxChanged[*] := 0
```

## 9. Design Patterns & Architecture

| Pattern / Decision | Implementation | Location | Purpose / Assessment |
|---|---|---|---|
| Message Handler / Command pattern | `case _MSG_MessageChat:` → `Exec_MSG_MessageChat` | `ProcessClientMessage.cpp:92` | Uniform opcode dispatch; handler name encodes the contract |
| Text-command multiplexer (poor-man's Command pattern) | `strcmp` chain, 9 literals, first match wins | `_MSG_MessageChat.cpp:37-169` | No registry, no table, no arity metadata; adding a command requires editing the function |
| In-place packet mutation / zero-copy relay | mutate `String`/`ID` then re-broadcast the same buffer | `:24-27`, `:178-193` | Saves a copy per recipient (1,088 copies avoided); makes `Size` normalization the handler's implicit responsibility (unmet) |
| Guard-clause (early return) validation | `Mode` gate, per-command returns | `:29`, `:47`, `:60`, `:101`, `:108`, … | Consistent "one branch, one return" style; makes the final `else` unreachable |
| Server-authoritative identity | `m->ID = conn` | `:27` | Anti-spoofing; the key security control of the component |
| Defensive re-termination | double NUL write before/after mutation | `:24-25`, `:178-179` | Compensates for the non-terminating `strncpy`; consumed 2 of 96 payload bytes |
| Latch / idempotency token | `TaxChanged[]` | `:82-89` | Prevents repeated file writes per cycle; reset point is in a different subsystem (coliseum) |

## Appendix B — Ethical / safety note on `GuildLevel` and identity fields

None of the privileges exercised by this component (`GuildLevel`, `MOB.Guild`, `MuteChat`, `GuildDisable`) are read from the client packet; they all come from server-side session or persisted character state. The component's own validation is therefore structurally sound against forgery, and the risks catalogued in §10 are implementation defects (format strings, missing size/rate checks, non-terminating copy, uninitialized buffer), not missing authorization checks.

# Design

## Context

See `proposal.md` for motivation and the delta specs for the behavior contract.

Current constraints that shape the approach:

- DBSrv is a single-threaded asio process. All game and admin callbacks run on the event-loop thread, and the current file store is synchronous, so every persistence call already blocks the loop.
- The on-disk record is a raw `STRUCT_ACCOUNTFILE` (7808 bytes) with four `STRUCT_MOB` (816), four `STRUCT_MOBEXTRA` (536), 128 `STRUCT_ITEM` cargo slots, and per-character affects. TMSrv sends whole `STRUCT_MOB`/cargo/affect snapshots and expects the same struct layouts back.
- Names are legacy byte strings and may not be valid UTF-8 (CP949 client). Any text column that receives raw names risks conversion failure.
- `STRUCT_ACCOUNTFILE` is also embedded in the NP admin protocol (`MSG_NPAccountInfo`), so its layout cannot change.
- Game flows depend on quirks encoded in `CFileDB`: negative-coin clamp, dated blocks, server-change token bypass, dual-sword name swap, `GetIndex` returning 0 on miss, and the in-memory slot `conn * MAX_USER + id`.
- Builds are 32-bit Windows x86 and Linux i386 with a pinned vcpkg baseline.

## Goals / Non-Goals

**Goals:**

- One relational model that can reconstruct the legacy structs exactly, including sparse arrays and zero-filled padding.
- One transaction per externally triggered mutation, with rollback on any failure.
- Credential hashing that fits the existing packet sizes and admin protocol without changing either.
- Deterministic, testable conversion of credentials and legacy files.
- A SQL layer that can be tested without a running game server.

**Non-Goals:**

- Async/non-blocking database access or a connection pool larger than one connection per process.
- Changing TMSrv, client packets, `STRUCT_ACCOUNTFILE`, `STRUCT_MOB` or `STRUCT_CAPSULE` layout.
- Migrating guild state, content CSVs, log files or the `ImportItem` hand-off format.
- Database-level encryption or key management beyond BCrypt hashing.
- Multi-node DBSrv coordination.

## Decisions

### D1. Use libpq directly behind a small storage wrapper

Add `libpq` from vcpkg and wrap it in `Code/storage/` with RAII handles (`PGconn`, `PGresult`), explicit `Result`/`bool` returns, and a transaction guard. Do not adopt libpqxx.

Rationale: the legacy code has no exception policy and returns `int`/`bool` everywhere; a C API wrapper keeps error handling on that path, avoids a second C++ API style in a `/permissive` MSVC build, and gives full control over binary parameter binding. libpqxx would save wrapper code but add an exception boundary and a heavier 32-bit build for no functional gain.

Alternative considered: libpqxx for prepared-statement ergonomics; rejected for the reasons above. Alternative: an ORM; rejected because the store is six operations wide and the record mapping is bespoke.

All SQL uses `PQexecParams` with bound parameters. Statements are named and prepared once per connection. Schema identifiers are compile-time constants.

### D2. Store raw legacy byte strings as `bytea`

Account names, character names, real name, e-mail, telephone and address are stored as `bytea` together with a normalized `name_key bytea` generated by the existing `UpcaseString`. Unique indexes use `name_key`.

Rationale: legacy names can be CP949 byte sequences that are invalid UTF-8; a `text` column would either reject them or require lossy conversion. Byte equality also matches the old path-based identity exactly. The admin and game protocols carry the same bytes in and out, so no encoding layer is introduced.

Alternative considered: `text` with `EUC_KR` conversion; rejected because it changes bytes for names that are not valid CP949 and adds a conversion failure mode on login.

### D3. One character entity for live characters and soul capsules

`w2pp.characters` holds both live characters (`account_id` and `slot` set) and sealed capsule payloads (`capsule_id` set, no account). Equipment, inventory, affects, extras and celestial saves reference `character_id`, so a character can be sealed and restored without copying child rows.

- `name_key` has a global unique index, which reproduces the legacy `./char` marker lifetime: sealing keeps the old name reserved, and take-out renames to the client-supplied name.
- `(account_id, slot)` is unique only for live rows.
- A check constraint enforces exactly one of `account_id` / `capsule_id`.
- `capsule_id` is a `smallint`-range sequence capped at 65535 because the capsule identifier is encoded into two item effect bytes (`item 3443`). Exhaustion fails the put-in instead of wrapping.

Alternatives considered: separate capsule tables (duplicated DDL and codec, no reuse); keeping capsules as bytea (contradicts the normalized-array goal for capsule equipment).

### D4. Child tables for arrays, sparse rows for empty positions

`character_equipment`, `character_inventory`, `account_cargo` and `character_affects` hold one row per non-empty position with a `position` column constrained to the legacy range. Missing positions reconstruct as zeroed entries (`item_index = 0`, all effects zero; affect type = 0).

Rationale: empty positions are identifiable by index 0 / type 0 in the legacy data, so a missing row is lossless. Storing all 128 cargo rows per account would multiply write volume by an order of magnitude for no information gain. Positions remain explicit, so sparse arrays round-trip exactly.

Alternatives considered: JSONB (weaker constraints and querying); bytea blobs (no relational access, but kept as the fallback for untested parts — none).

### D5. `STRUCT_ACCOUNTFILE` stays the in-memory and wire representation

`Code/storage/RecordCodec` converts between the unchanged structs and repository row structs. `STRUCT_ACCOUNTFILE`, `STRUCT_MOB`, `STRUCT_MOBEXTRA`, `STRUCT_CAPSULE` and their guards remain untouched. `DBReadAccount`/`DBWriteAccount` keep their signatures and now call the repository.

- The reader zeroes the destination before filling it, removing the current uninitialized-tail bug while preserving observable values.
- Padding and the `EMPTY` arrays are not stored and reconstruct as zero.
- `Info.AccountPass` is always zero-filled on read; `NumericToken` follows the token-set flag.
- `pAccountList` keeps its `MAX_DBACCOUNT` slots. A new in-memory `account_id` on `STRUCT_ACCOUNTLIST` (not part of any record or packet) avoids repeated name lookups.

### D6. Schema (initial version 1)

Schema `w2pp`:

- `schema_migration(version int primary key, applied_at timestamptz)`
- `store_metadata(key text primary key, value text)` — holds `import_state` (`pending` / `complete` / `failed`) and the schema contract version.
- `accounts` — `account_id`, `name bytea`, `name_key bytea unique`, `password_hash text`, `token_hash text null`, `state smallint` (0 normal, 1 blocked, 2 deleted, 3 disabled), `real_name`, `ssn1`, `ssn2`, `email`, `telephone`, `address`, `block_year`, `block_year_day`, `temp_key bytea(52)`, `coin int`, `donate int`, `short_skill bytea(64)`, failure counters and lockout timestamps, `created_at`, `updated_at`.
- `characters` — identity `character_id`, nullable `account_id`/`slot`/`capsule_id`, `name bytea`, `name_key bytea unique`, then every scalar `STRUCT_MOB` field: clan, merchant, guild, class, rsv, quest, coin, exp (bigint), spx, spy, learned_skill, magic (bigint), score/special/skill bonuses, critical, save_mana, skill_bar bytea(4), guild_level, regen_hp, regen_mp, resist as four smallints, and `base_*` / `current_*` score columns (level, ac, damage, merchant, attack_run, direction, chaos_rate, max_hp, max_mp, hp, mp, str, int, dex, con, and four special smallints).
- `character_equipment` / `character_inventory` — `(character_id, position)` primary key, `item_index smallint`, `effect0..2 smallint`.
- `account_cargo` — `(account_id, position)` primary key, same item columns.
- `character_affects` — `(character_id, position)` primary key, `type smallint`, `value smallint`, `level integer`, `time bigint` (unsigned 32-bit stored wide).
- `character_extras` — one row per character: class_master, citizen, fame, soul, mortal_face, mortal/arch/celestial/circle quest fields, last_nt, nt, kefra_ticket, divine_end, hold, daylog_exp, daylog_year_day, donate_last_time, donate_count.
- `character_celestial_saves` — `(character_id, save_slot 0..1)` with the `SaveCelestial` block (class, exp, spx, spy, base score, learned skill, bonuses, skill bar bytes, soul).
- `credential_events` — append-only audit of failed/locked verifications (account id, credential kind, occurred_at, source); no credential material.

All scalar columns are `NOT NULL DEFAULT 0` unless they represent absence (token hash, capsule link). `updated_at` on `accounts` is the replacement for the file mtime used by the day-log and ranking scans.

Indexes: `characters(account_id, slot) unique where account_id is not null`, `characters(name_key)` unique, `characters(capsule_id) unique where capsule_id is not null`, `characters(account_id)`, `character_* (character_id)`, `accounts(updated_at)`, `accounts(name_key)`.

### D7. Read/write batching and transactions

One repository call maps to one transaction:

- **Load account**: `BEGIN ISOLATION LEVEL REPEATABLE READ`; fetch the account row, its character rows, equipment/inventory by character ids, affects, extras and celestial saves; assemble the struct; commit.
- **Save account**: update the account row; upsert each changed character; replace child rows only for arrays whose bytes differ from the cached snapshot; commit.
- **Delete character / put-in capsule / take-out capsule / create character / password change / token bind**: single transaction that also enforces uniqueness and locks the account row (`SELECT ... FOR UPDATE`) where the legacy code relied on serialized file access.
- **Login admission**: one transaction covering the read, the coin clamp persistence, temp-key clear and hashing upgrade, so a crash cannot leave half-admitted state.

Prepared statements are named per operation. `statement_timeout` and `lock_timeout` are set from configuration (defaults 5s and 2s). Every failure path rolls back and logs the SQLSTATE and operation name, never parameter values.

Writes use `INSERT ... ON CONFLICT` upserts keyed by identity columns, and child rows are deleted/re-inserted per affected array inside the same transaction.

### D8. Credentials: BCrypt via a vendored reference implementation

`Code/security/PasswordHash` wraps a vendored, permissively licensed BCrypt implementation (OpenBSD/`crypt_blowfish` lineage) compiled as a static target. No system `crypt(3)` dependency, and it builds on 32-bit MSVC and Linux.

- `Generate(credential, cost) -> "$2b$..."`; `Verify(credential, hash) -> bool`; `NeedsRehash(hash, cost) -> bool`.
- Cost: default 12, minimum 10, maximum 14 (accepted range); configured in `Config.txt` / environment.
- Password and token use the same policy. `token_hash IS NULL` is the unset state; the legacy `NumericToken[0] == -1` sentinel maps to it.
- Verification extracts the exact credential bytes: up to 16 bytes from the legacy field, terminated at the first NUL, case-sensitive. New input is limited to 15 bytes as today. Legacy 16-byte non-terminated values are hashed byte-for-byte so they remain verifiable.
- Successful verification with a hash below the current cost rehashes inside the same transaction.
- Hashing stays in DBSrv; TMSrv forwards bytes unchanged.

Alternatives considered: libsodium (Argon2id, not BCrypt); `crypt(3)` (unavailable on MSVC); Windows CNG (not BCrypt password hashing despite the name).

### D9. Account state and throttling

State replaces the password-prefix marker convention:

| Legacy password prefix | New |
| --- | --- |
| `@` | `state = blocked` |
| `_` | `state = deleted` |
| `#` | `state = disabled` |
| other | `state = normal` |

The dating fields (`block_year`, `block_year_day`) stay separate; login refuses when either the state is not `normal` or the date is in the future. The NP reply keeps state values 0–3.

Failed verification counters live on `accounts` per credential kind (`password_failures`, `password_locked_until`, `token_failures`, `token_locked_until`). Defaults: 5 failures, 15 minutes, reset on success. The in-memory `SecurePass` session flag and TMSrv's existing `CheckFailAccount` remain unchanged.

### D10. Configuration

`Config.txt` stays the primary file and keeps its first two lines for compatibility. New keys are appended as `Key Value` lines:

```
PgHost 127.0.0.1
PgPort 5432
PgDatabase w2pp
PgUser w2pp
PgSslMode prefer
BcryptCost 12
AuthMaxFailures 5
AuthLockoutSeconds 900
```

- Every key can be overridden by `W2PP_PG_HOST`, `W2PP_PG_PORT`, `W2PP_PG_DATABASE`, `W2PP_PG_USER`, `W2PP_PG_PASSWORD`, `W2PP_PG_SSLMODE`, `W2PP_BCRYPT_COST`, `W2PP_AUTH_MAX_FAILURES`, `W2PP_AUTH_LOCKOUT_SECONDS`.
- The password is never written to `Config.txt`; it comes from the environment, `PGPASSWORD`, or a libpq password file.
- `LastCapsule` is read only by the importer; DBSrv no longer persists it.
- Startup: connect, verify `store_metadata.schema_contract`, apply pending migrations (transactional, advisory-locked), require `import_state = complete`, then listen. Any failure aborts startup with a non-zero exit.

### D11. Importer

A separate `dbimport` executable links the storage and security modules and runs outside DBSrv:

```
dbimport --source <legacy root> --dsn <...> [--dry-run] [--replace] [--report <file>] [--legacy-export <dir>] [--empty]
```

Steps: acquire an advisory lock; migrate/verify schema; walk `./account/<bucket>/*`; accept the same size window as the ranking loader; reject empty or structurally invalid records; normalize names with `UpcaseString`; hash password/token; map prefix states; upsert by `name_key`. Verify `./char/<bucket>/<NAME>` markers against imported characters and report mismatches. Import `./capsule/<n>` as sealed character rows and set the capsule sequence above the maximum id plus the legacy `LastCapsule`. Re-run: identical rows are skipped; differing rows require `--replace`. Verification: per-account structural checksum (FNV-1a over defined fields) before and after; counts of accounts, characters, capsules and rejected files. Only a run with zero rejects and matching counts sets `import_state = complete`; otherwise it records `failed` and exits non-zero. `--empty` initializes an intentionally empty production store.

`--legacy-export <dir>` writes a complete `STRUCT_ACCOUNTFILE` tree from the database (including empty password/token fields) so the previous binary can be restored after cutover.

### D12. Scan replacements

- **Day-log**: accounts with `updated_at` in the current local month; characters where `daylog_year_day = yesterday_of_year`. Month boundaries are computed in C++ local time and passed as parameters, preserving `localtime` semantics rather than the database session timezone. Output line format is unchanged.
- **Ranking**: accounts with `updated_at` in the current year and month >= current month - 1 (matching the legacy `year == current && month < current-1` skip, including its January behavior), characters with a non-empty name and `current_level < 1000`; same `tryInsertInRanking` call order as the legacy loop.
- **Character lookup by name**: `SELECT account_id FROM characters WHERE name_key = $1 AND account_id IS NOT NULL`.

### D13. Build and test wiring

- `vcpkg.json`: add `libpq` to the manifest. BCrypt is vendored under `third_party/bcrypt` with its license file.
- `CMakeLists.txt`: new `w2pp_storage` static library (storage + security + codec) linked by `dbsrv`, `dbimport`, the unit tests and a new `w2pp_db_tests` executable.
- Unit tests (no database): codec round-trip against generated `STRUCT_ACCOUNTFILE` values, sparse arrays, checksum stability, BCrypt vectors, cost/`NeedsRehash`, credential byte extraction.
- Integration tests (Catch2) under `tests/db/`: schema apply and rollback, CRUD and upserts, transaction rollback, unique constraints, capsule sequence, importer idempotence and rejects, query parity. Each run creates a fresh database (`w2pp_test_<pid>`), applies migrations, runs, then drops it.
- `tests/db/docker-compose.yml` pins `postgres:19.0` with a healthcheck and a non-conflicting host port (default 55432, overridable). Runners `tests/db/run_db_tests.ps1` and `run_db_tests.sh` start the stack, wait for health, invoke `w2pp_db_tests` with the DSN, and always tear down with volume removal.
- CTest registers `db-integration` when `W2PP_DB_TESTS` is ON (default) and Docker is found; configure prints a status line when the test is skipped, and `-DW2PP_DB_TESTS=OFF` is the documented opt-out for hosts without a container runtime. The test binary exits with CTest's skip code 77 when no DSN is present, so direct invocation without Docker is also explicit.

## Risks / Trade-offs

- **Blocking event loop**: synchronous libpq calls and BCrypt verification run on the single asio thread. → Statement/connect/lock timeouts bound the worst case; queries are primary-key lookups; BCrypt cost is configurable down to 10 on constrained hosts. Moving authentication to a worker pool is a follow-up, not part of this change.
- **Low-entropy token**: a 4–6 digit token is guessable offline if the hash leaks. BCrypt raises the cost per guess, and the per-account lockout blocks online guessing, but offline guessing remains feasible at the low end. → Documented as residual risk; operators should prefer 6-digit tokens; a server-side pepper is a possible follow-up.
- **CP949 names and `bytea`**: operators lose readable SQL output for names. → Provide helper views using `convert_from(name,'EUC_KR')` where valid, but keep storage byte-exact.
- **Importer fidelity**: any field not mapped is silently zeroed. → Structural checksums, a fixture with every field populated, and a reject on checksum mismatch; `--dry-run` and `--report` before cutover.
- **32-bit libpq availability**: the vcpkg port must build for `x86-windows` and `x86-linux`. → Validate with a dependency spike before the storage work; if unavailable, fall back to building libpq from source in the manifest overlay and record the decision.
- **BCrypt cost on legacy hardware**: cost 12 can take hundreds of milliseconds per login on old CPUs. → Configurable cost and lockout; monitor login latency; the default remains 12 per spec.
- **Admin tool assumptions**: the NP tool may not expect an empty password field. → The save path ignores the submitted password and re-reads the hash, so edits cannot corrupt credentials; document the display change for operators.
- **Schema ownership**: DBSrv needs DDL privileges when migrations run. → Support a separate `dbmigrate` invocation using the same migration code and start DBSrv with a runtime role that only has DML.
- **Capsule identifier exhaustion**: 16-bit encoding caps capsules at 65535. → Sequence `MAXVALUE 65535`, put-in fails with a logged error instead of wrapping.
- **Docker dependency in tests**: default test run needs a container runtime. → Opt-out switch, clear configure status, and CI documentation.

## Migration Plan

1. **Prepare**: provision PostgreSQL 19, a database and roles (runtime DML role, migration role). Configure `Config.txt` and the password environment variable.
2. **Spike and build**: confirm libpq builds for both triplets, then build the storage, security, importer and DBSrv changes.
3. **Dry run**: stop DBSrv; run `dbimport --dry-run --report import-dry.txt` against a copy of the legacy tree; review rejects.
4. **Import**: run `dbimport --source <tree> --report import.txt`. Success requires zero rejects and `import_state = complete`.
5. **Smoke test**: start DBSrv against the imported store; verify login for a normal, a blocked and a token-protected account; verify save, capsule put-in/take-out and the ranking report.
6. **Cutover**: keep the legacy tree untouched. Run the new DBSrv as the only writer. Archive the tree after an agreed observation window.
7. **Rollback**: before cutover, stop the new DBSrv and start the previous binary (files unchanged). After cutover, run `dbimport --legacy-export <dir>`, verify the exported tree, then start the previous binary.
